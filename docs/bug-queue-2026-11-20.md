## 1. gbrain health check with a Slack alert when it stops answering

**Why:** gbrain-mcp (port 7700) wedged on Nov 20 (~12:21–12:49 UTC), as on Oct 5–6. bun was at 99.5% CPU, the main
thread was running, and the listen queue held 437 connections it never accepted. It made no outbound calls (it was
not waiting on ollama). Nothing alerted: the only signal was QA turns slowing to 60–135 s. Production turns waited
15 s per memory call (rachel, rachel-mcp, shopping-agent and rachel-slack all use it). Fixed by
`sudo systemctl restart gbrain-mcp`. SIGTERM was ignored, so systemd SIGKILLed it after 90 s.

**Idea:** a monitor detector (ops/monitor.py) or a cron check every minute or two:
- `ss -ltn` Recv-Q on :7700 above a threshold;
- `curl -m 5 http://127.0.0.1:7700/` gets no answer (a live server returns 404 in a few ms);
- `[gbrain] error: no answer in 15000ms` lines spiking in rachel.log.

Post to OPS_SLACK_CHANNEL in plain words ("customer memory has stopped answering — every reply is ~15 s slower").
Restarting needs DC's OK (rule 2), so alert, don't auto-restart, unless DC decides otherwise.

**Evidence:** this session's checks (CLAUDE.md "gbrain wedge" note); staging log at the time showed 166 gbrain
timeouts in one smoke run (get_page 108, put_page 33, query 25).

## 2. Circuit breaker: skip memory for a few minutes after repeated gbrain failures

**Why:** while gbrain is down, every call still waits the full 15 s (GBRAIN_TIMEOUT_MS), several times per turn, so
a turn takes 60–135 s instead of a few seconds.

**Idea:** in rachel/gbrain.js (and the shopping-agent's gbrainFetch), after N consecutive timeouts or connection
failures (say 3 in 60 s), open the breaker for M minutes (say 3). While it is open, return "no memory" at once and
log `[gbrain] circuit open — skipping memory (N failures, retry at HH:MM)`. Then let one probe call through and close
on success. Log every open and close (rule 7). The same applies to rachel-mcp and rachel-slack (rule 8: every channel).

## 3. gbrain-mcp unit: stable admin token, not printed to the log (needs DC's approval — systemd change)

**Why:** gbrain prints a fresh "Admin Token (paste into /admin login)" banner on every start to logs/gbrain-mcp.log
(StandardOutput=append). The file holds 184 of them. On Nov 20 a plain `tail` of that file printed one into a
session.

**Change:** in the gbrain-mcp unit, set `GBRAIN_ADMIN_BOOTSTRAP_TOKEN` (strong: `[A-Za-z0-9_-]{32+}`, else gbrain
refuses to start; from a root-only EnvironmentFile, not inline) and add `--suppress-bootstrap-token` to ExecStart
(`bun run src/cli.ts serve --http --port 7700 --suppress-bootstrap-token`). Source:
~/gbrain/src/commands/serve-http.ts (resolveBootstrapToken, ~line 495; banner ~line 2145).

Then decide whether to scrub the old banners from logs/gbrain-mcp.log, or rotate the file.

Separate secret, unchanged by this: `GBRAIN_TOKEN` in /etc/gbrain.env (EnvironmentFile of rachel, rachel-mcp,
shopping-agent and rachel-slack; read in rachel/gbrain.js, rachel/package-model.js, rachel/rachel_slack_bot.py and
store-agent/shopping-agent.js). DC plans to rotate both in one go after this deploy.
